# 運用形態の決定（2026-08-05）

## 決定事項

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| アクセス範囲 | **事務所の中だけ。社内LAN で完結する** | 現場のタッチモニター運用が前提。外部から見る要件は無い |
| 月額費用 | **0円。外部サービスに一切課金しない** | 手間が増えても無料の道を選ぶ |
| Vercel | **使わない** | Hobby プランは非商用限定で、会社の業務システムは規約違反。Pro は $20/月 |

## これに伴う見直し（着手時に確認すること）

- **ホスティング**: 事務所の PC 1台をサーバーにして、そこでアプリを動かす。
  現場のタッチモニターからは LAN 内の IP で見る。
- **Supabase をどうするか — 未決定。**
  - Supabase の無料枠自体は 0円で、商用利用も禁じられていない（Vercel と違う点）。
  - ただしクラウド DB に依存すると、**事務所のインターネットが落ちた日に配車盤が止まる。**
    毎日の運用に使うものなので、この停止リスクは軽くない。
  - 代替: 事務所 PC 上の PostgreSQL、または SQLite。完全にオフラインで動く。
  - 既に Supabase プロジェクト「ボイスロジ」は作成済み（AWS ap-northeast-1 / Nano）。
- **認証・RLS**: Supabase Auth を前提にしていたが、LAN 内運用なら要件が変わる。再検討。
- **Realtime による複数端末同期**: 要件自体は生きている。LAN 内サーバーでどう実現するか再設計が要る。
- **Next.js を採用し続けるか。** `next start` を事務所 PC で動かす構成は可能。
  ただし PR #1 の Flask 版（`run_server.py` が `0.0.0.0:8000` で LAN 配信）は
  **まさにこの要件のために作られている。** 作り直す前に、そちらを活かす選択肢も比較すること。

## 注意

この決定は**技術選定より上位の制約**。
「Vercel が楽だから」「Supabase が標準だから」という理由でここを覆さない。
覆す必要が出たら、必ず本人に相談する。
