# KoeHaisha フェーズ1 現場導入チェックリスト

**フェーズ1の完成基準は「プログラムが動くこと」ではなく「現場で実際に毎日使える状態になること」とする。** コードの実装・ビルド成功・画面確認はあくまで前提条件であり、これ単体をもってフェーズ1完了とはしない。

当社は土木部門と運送部門の両方で使うため、この2部門どちらでも違和感なく使える運用であることを前提に、以下を整理する。

## 1. フェーズ1で残っている課題（実装の中身に関する課題）

### 導入前に必ず解消すべきもの

| # | 課題 | 内容 |
|---|---|---|
| 1 | 氏名の正確性が未検証 | `seed.ts`の氏名は写真からの読み取りであり、誤読の可能性がある。現場で全員分を確認・修正していない |
| 2 | 実機での見え方が未確認 | ブラウザでの画面確認のみ。実際に使う縦型タッチパネルの解像度・画面比率・タップ精度・日光下や作業服手袋での操作感は未検証 |
| 3 | 管理画面(`/admin`)にアクセス制限がない | URLを知っていれば誰でも社員の追加・編集・削除ができる。共用のタッチパネルに置く場合、意図しない操作のリスクがある |
| 4 | 状態セットが土木・運輸で本当に共通でよいか未検証 | 「空車」は運輸（配車待ち）の概念としては自然だが、土木の作業員にとって違和感がないか、実際に現場の人に見てもらって確認していない |

| # | 課題 | 内容 |
|---|---|---|
| 5 | デプロイスクリプトが実機未検証 | `webapp/deploy/`一式は雛形段階。実際の端末（機種・OS）でパスを調整し、自動起動・キオスク表示・再起動後の継続動作を確認していない |
| 6 | バックアップの動作未検証 | `backup.sh`をcron/タスクスケジューラに実際に登録し、正しく世代管理されるか確認していない |
| 7 | 人数が増えた場合の表示未検証 | 現状32名程度で確認。人数増加時の縦スクロール量・一覧性は未検証 |
| 8 | 「元に戻す」は直前1回分のみ | 連続して操作を間違えた場合、2つ前には戻せない仕様。現場運用で十分か要確認 |

## 2. 現場導入までに必要な作業一覧

1. **実機の確定**：実際に使うタッチパネルの機種・OS・画面解像度を決め、Node.jsが動作するか確認する。
2. **実機でのセットアップ検証**：`deploy/`のスクリプトを実機のパスに合わせて調整し、自動起動〜キオスク表示〜再起動後の継続動作までを通しで確認する。
3. **正式な氏名・部門リストの確認**：会社から正式な社員名簿（土木・運輸両方）をもらい、`seed.ts`または管理画面で正確なデータに置き換える。
4. **現場担当者による試用とフィードバック**：実際に配車担当・現場責任者に触ってもらい、文字の大きさ・タップのしやすさ・状態の名称が実務に合っているかを確認する。特に土木側の担当者にも必ず触ってもらう（運輸目線だけで決めない）。
5. **バックアップ運用の明文化**：保存先・世代数・誰がいつ確認するかを簡単なルールとして決める。
6. **管理画面のアクセス制御方針の決定**：URLを知っている人だけに限定する運用にするか、簡単なパスワードを設けるか等を決める（フェーズ1の範囲でどこまでやるかは要相談）。
7. **障害時の対応手順の整備**：サーバーが落ちた・端末がフリーズした場合にどうするか、誰に連絡するかを簡単にまとめる。
8. **移行期間の検討**：紙の札を急に廃止せず、最初の数日〜1週間は紙と併用して運用に慣れてもらう期間を設けるか判断する。

## 3. フェーズ2へ進む前に確認すべき事項

1. **応援・異動の実際の頻度**：`home_department`／`current_department`を分けたが、フェーズ1では日々の切替UIを作っていない。実際の運用でどのくらいの頻度・緊急度で部門をまたぐ応援が発生するかを、フェーズ1運用を通じて見極めた上で、フェーズ2で切替UIが必要か判断する。
2. **車両側の状態設計**：フェーズ1で「整備」を人の状態から外した。フェーズ2で車両マスタを作る際、車両の状態（空車／稼働中／整備中等）をどう設計するかを改めて詰める。
3. **会社名・車両番号のマスタ管理方法**：配車機能で使う会社名・車両番号を、誰がどうやってデータ登録・更新するか（社員管理画面のような簡易画面を作るか、Excel等からの取り込みにするか）。
4. **音声入力・請求書機能の優先順位**：フェーズ2でどこまでやり、何をフェーズ3以降に回すか。
5. **複数端末・複数拠点対応の要否とタイミング**：SQLiteのままでよいか、PostgreSQL等への切替が必要になるタイミングをどう見極めるか。
6. **操作者の記録（ログイン・権限）の要否**：フェーズ1では「誰が変更したか」を記録していない。フェーズ2以降で必要になるか。
7. **フェーズ1の本番運用期間の確保**：フェーズ2に着手する前に、最低どのくらいの期間フェーズ1を実運用し、そこで出た課題・要望を反映する期間を設けるか。
