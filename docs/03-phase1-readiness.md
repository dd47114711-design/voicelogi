# KoeHaisha フェーズ1 現場導入チェックリスト

**フェーズ1の完了基準は「プログラムが動くこと」ではなく「土木・運輸どちらの現場担当者も、紙の代わりとして毎日問題なく使えている」ことである。** コードの実装・ビルド成功・画面確認はあくまで前提条件であり、これ単体をもってフェーズ1完了とはしない。

「システム機能の課題」と「現場に導入するための作業」は別物のため、章を分けて整理する。

---

## A. システム機能に関する残課題（アプリの中身の問題）

出欠画面・社員管理・状態変更など、コードを直さないと解決しない項目。

| # | 課題 | 内容 | 状態 |
|---|---|---|---|
| A1 | 管理画面(`/admin`)にアクセス制限がない | URLを知っていれば誰でも社員の追加・編集・削除ができる | **解消済み**：`ADMIN_PASSWORD`による簡易パスワード保護を実装（`/admin`画面と書き込み系APIが対象、出欠札ボード本体とタップでの状態変更は対象外） |
| A2 | 「応援」を正しく表せない | `home_department`（本来の所属）を保ったまま当日だけ`current_department`を切り替えたい | **解消済み**：管理画面に「◯◯へ応援」／「応援解除」ボタンを追加。応援中は名札に「応援」バッジを表示 |
| A3 | 状態セットが土木・運輸で本当に共通でよいか未検証 | 「空車」は運輸（配車待ち）の概念としては自然だが、土木の作業員にとって違和感がないか、実際に土木側の人に見てもらって確認していない | 未検証（導入前に解消） |
| A4 | 人数増加時の表示が未検証 | 現状32名程度で確認。人数がさらに増えた場合の縦スクロール量・一覧性は未検証 | 未検証（導入後でも可） |
| A5 | 「元に戻す」は直前1回分のみ | 連続して操作を間違えた場合、2つ前には戻せない仕様。現場運用で十分か要確認 | 未検証（導入後でも可） |
| A6 | 削除の取り消しUIがない | 社員削除は`is_active=false`のソフトデリートでデータ自体は残るが、画面から復活させる手段がなく、開発者によるPrisma Studioでの操作が必要 | 未解消（導入前に解消） |
| A7 | 同姓同名の判別手段がない | 一覧・編集とも「氏名」のみで管理しており、完全に同じ氏名の社員がいた場合に見分ける手段がない | 現時点で該当者なしと確認済み。今後発生したら要対応 |
| A8 | サーバーの実行場所が未確定 | Webアプリ本体（Next.jsサーバー）をどこで動かすかが未確定。KTC MEGAPAD(Android)上で直接動かすのか、別の常時起動PC(Windows/Linux等)で動かしてMEGAPADはブラウザ表示専用にするのかで、B1・B2の作業内容が変わる。後述B章参照 | **要方針決定** |

## B. 現場導入作業（システムそのものではない、現場に置くための作業）

コードではなく、機材の選定・データの確認・現場での試用・運用ルール作りなど、人が行う作業。

| # | 作業 | 内容 |
|---|---|---|
| B1 | タッチパネルの機種は決定済み（32インチ KTC MEGAPAD、Android搭載） | 標準ブラウザ(Chrome等)で動くWebアプリのため専用アプリは不要。ただしA8の通り、**Node.jsサーバーをどこで動かすか**は別途決める必要がある |
| B2 | サーバーの実行場所の決定と実機セットアップ | A8を決定した上で、`webapp/deploy/`のスクリプトを実機構成に合わせて調整する。KTC MEGAPAD(Android)上でキオスク表示させる方法は、`deploy/`のLinux/Windows向けスクリプトとは別に用意する必要がある（例：Androidの「常時起動アプリ」設定、Fully Kiosk Browser等のキオスク専用ブラウザアプリの利用）。自動起動〜キオスク表示〜再起動後の継続動作までを通しで確認する |
| B3 | 正式な氏名・部門データの確認 | 会社から正式な社員名簿（土木・運輸両方）をもらい、写真からの読み取りデータを正確なものに置き換える |
| B4 | 現場担当者による試用 | 配車担当・現場責任者に実機で触ってもらう。**土木側の担当者にも必ず触ってもらい**、運輸目線だけで判断しない |
| B5 | バックアップ運用の明文化 | 保存先・世代数・誰がいつ確認するかを簡単なルールとして決め、`backup.sh`を実際にcron等へ登録して動作確認する |
| B6 | 障害時対応手順の整備 | サーバーが落ちた・端末がフリーズした場合にどうするか、誰に連絡するかを簡単にまとめる |
| B7 | 紙との移行期間の検討 | 紙の札を急に廃止せず、最初の数日〜1週間は紙と併用して運用に慣れてもらう期間を設けるか判断する |

## C. 現場で起こり得る運用パターンの洗い出し

現場運用で想定されるパターンをすべて洗い出し、「フェーズ1で対応するもの」と「フェーズ2以降へ回すもの」を分類する。後から仕様変更が発生しにくいよう、データの持ち方は多くのケースで先回りして用意してあるが、UI（画面上の操作）として対応しているかは別に評価する。

### 部門・所属に関するパターン

| パターン | 分類 | 対応状況 |
|---|---|---|
| 土木→運輸へ応援（一時的、本来の所属は土木のまま） | **要方針決定** | データ構造(`home`/`current`)は用意済みだが、本来の所属を保ったまま当日だけ表示を変えるUIが未実装（A2参照）。フェーズ1のうちに軽い「本日だけ他部門表示」ボタンを追加するか、フェーズ2に回すか要相談 |
| 運輸→土木へ応援（同上） | 同上 | 同上 |
| 配置換え（恒久的な部門異動） | **フェーズ1で対応** | 社員管理画面の「所属編集」で対応可能（本来の所属ごと変更するため） |
| 協力会社・派遣の作業員がその日だけ入る | **フェーズ1で応急対応可・正式対応はフェーズ2** | 社員として追加→使い終わったら削除、で応急的に対応可能。ただし「自社社員」と「協力会社」を区別する仕組みはない |

### 人の状態に関するパターン

| パターン | 分類 | 対応状況 |
|---|---|---|
| 1日に何度も状態が変わる（午前現場→午後空車 等） | **フェーズ1で対応** | 回数制限なくタップで変更可能 |
| 半休（午前休・午後休） | **フェーズ2以降** | フェーズ1の状態には時間の概念がない。当面は「その他」等で代用 |
| 直行直帰 | **フェーズ1で対応** | 「現場」状態で表現可能。出社有無を記録する必要はない想定 |
| 遅刻・早退 | **フェーズ1のスコープ外** | 本アプリは勤怠（出退勤時刻）管理システムではなく状態表示ボードのため、時刻の記録自体を目的としない |
| 急な欠勤（当日朝に休みへ変更） | **フェーズ1で対応** | 「休み」にタップ変更するだけで対応可能 |
| 長期休暇（産休・病欠等、数週間〜数ヶ月） | **フェーズ1で最低限対応・理由記録はフェーズ2** | 「休み」状態のまま長期間置ける。ただし「なぜ休みか」を記録する項目はない |

### 車両に関するパターン（人と車両が別々に動く）

| パターン | 分類 | 対応状況 |
|---|---|---|
| 車両は整備中だが人（運転手）は出勤扱い | **フェーズ2** | フェーズ1に車両データ自体が存在しないため、車両単位の状態は記録できない。人の状態は「出勤」のままでよく矛盾はしない |
| 人は休みだが車両は他の人が使用 | **フェーズ2** | 同上。人と車両を別エンティティとして持つ配車機能が必要 |
| 複数現場の掛け持ち（現場名までは記録） | **フェーズ2** | フェーズ1は「現場」という状態のみで、どの現場かは記録しない |

### 社員データに関するパターン

| パターン | 分類 | 対応状況 |
|---|---|---|
| 新人が入社 | **フェーズ1で対応** | 管理画面から追加可能 |
| 退職者が出る | **フェーズ1で対応** | 管理画面から削除（非表示化）可能。履歴は残る |
| 同姓同名の社員がいる | **要確認** | 判別手段がない（A7参照）。実際に該当者がいるか要確認、いる場合は表示に一工夫必要 |
| 結婚等による改姓 | **フェーズ1で対応** | 管理画面から氏名編集可能 |
| 誤って削除した社員を戻したい | **要確認** | データは残るが復活させるUIがない（A6参照） |

### システム運用に関するパターン

| パターン | 分類 | 対応状況 |
|---|---|---|
| 通信が一時的に切れる（同一端末内での障害） | **フェーズ1で対応済み** | 通信失敗時は変更前の状態に戻し、エラーメッセージを表示する仕組みを実装済み |
| 複数端末・複数拠点から同時に見たい/操作したい | **フェーズ2以降** | 現状は1端末での利用を前提としたSQLite構成。複数端末対応にはDB構成の見直しが必要 |
| 端末が故障する | **導入作業(B章)で対応** | データはSQLiteファイルとして残るため、バックアップ運用(B5)と組み合わせて復旧する |
| 誤操作からの復旧（取り消し漏れ） | **フェーズ1で一部対応** | 直前1回分は「元に戻す」で対応可能(A5の制限あり) |

## D. フェーズ2へ進む前に確認すべき事項

1. **応援・異動の実際の頻度**：フェーズ1運用を通じて、部門をまたぐ応援がどのくらいの頻度・緊急度で発生するかを見極めた上で、A2の切替UIをフェーズ1のうちに追加するか、フェーズ2に回すかを判断する。
2. **車両側の状態設計**：フェーズ1で「整備」を人の状態から外した。フェーズ2で車両マスタを作る際、車両の状態（空車／稼働中／整備中等）をどう設計するかを改めて詰める。
3. **会社名・車両番号のマスタ管理方法**：配車機能で使う会社名・車両番号を、誰がどうやってデータ登録・更新するか。
4. **協力会社・派遣作業員の扱い**：自社社員と区別する仕組みが必要か、C章の「協力会社の作業員」パターンを踏まえて検討する。
5. **半休・遅刻早退等、時間単位の粒度が必要か**：勤怠管理としての機能を持たせるか、現状通り状態表示に留めるかを判断する。
6. **音声入力・請求書機能の優先順位**：フェーズ2でどこまでやり、何をフェーズ3以降に回すか。
7. **複数端末・複数拠点対応の要否とタイミング**：SQLiteのままでよいか、PostgreSQL等への切替が必要になるタイミングをどう見極めるか。
8. **操作者の記録（ログイン・権限）の要否**：フェーズ1では「誰が変更したか」を記録していない。フェーズ2以降で必要になるか。
9. **フェーズ1の本番運用期間の確保**：フェーズ2着手前に、最低どのくらいの期間フェーズ1を実運用し、そこで出た課題・要望を反映する期間を設けるか。

## フェーズ1の完了条件（再掲・確定）

以下がすべて揃った時点でフェーズ1完了とする。コードの完成・ビルド成功だけでは完了としない。

- 上記「A. システム機能に関する残課題」のうち「導入前に解消」「要方針決定」「要確認」の項目がすべて解消・決着している
- 上記「B. 現場導入作業」がすべて完了している
- 上記「C. 運用パターン」の分類について合意が取れている
- 実際に土木・運輸両方の現場担当者が、紙の代わりとして毎日問題なく使えている（最低1〜2週間の実運用で確認）
