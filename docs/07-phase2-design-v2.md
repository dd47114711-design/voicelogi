`06-phase2-design-proposal.md`（初版）に対するご回答を反映した修正版です。**まだ実装していません。** 内容をご確認いただいた後、フェーズ2Aから段階的に着手します。

初版からの主な変更点：
- 現場区分と部門（社員の所属）を完全に独立させた
- フェーズ2の範囲を「マスタ管理（2A）」＋「当日の現場配置（2B）」に拡大
- 車種違いは「別現場」ではなく「同じ現場の中の車種別単価」として扱う構造に変更

## 3. 出欠ボードから現場配置までの操作フロー

1. 配車担当がボードを開く（起動時は「部門別」表示）
2. 名札をタップすると、これまで通り状態選択（出勤／現場／空車／休み／その他）に加えて、「現場：未定」または「現場：〇〇現場」というボタンが表示される
3. 「現場を選ぶ」をタップすると、取引先ごとにまとめた現場一覧（検索欄あり、件数が多いため）が開く
4. 現場をタップすると、その場で当日の配置として確定（本来の所属`home_department`は変更しない）
5. ボード上部の「現場別」タブに切り替えると、現場ごとに配置人数付きで社員が表示される。現場未配置の人は「現場未定」の枠にまとまる
6. 名札には常に、配置されている現場名が小さく表示される（現場未定の場合は表示なし）
7. 配置を解除したい場合は、名札をタップ→「現場を選ぶ」→一覧の先頭にある「未定に戻す」をタップ
8. 休みにした人は、部門別・現場別どちらの表示でも一番下の「休み」エリアにまとまる（現場配置の状態に関わらず優先）

## 4. 車種別単価のデータ構造

ご指示のとおり、「取引先 → 現場 → 車種別単価」の3層構造にします。同じ現場が複数の車種で異なる単価を持つ場合は、現場を分けず、`SitePrice`の行を車種の数だけ持たせます。

```
取引先：㈱俵口建設
└─ 現場：（現場名）
    ├─ 車種別単価：10tダンプ　昼24,000円（元データの「標準」行）
    └─ 車種別単価：4t車　昼24,000円
```

配車時に単価を表示する際は、「現場」を選んだ後に「車種」を選ぶと、該当する`SitePrice`（`validTo`が空欄の最新のもの）が表示される、という流れを想定しています（実際の配車画面はフェーズ2の対象外のため、データ構造としてこれに対応させておくだけに留めます）。

## 5. 86社分のデータの振り分け方（方針）

分析済みの`scripts/genba_master_draft.json`をもとに、以下の方針で振り分けます（実際の変換は2A-2の実装時にスクリプトとして作成します）。

## 7. 確認事項の決定内容

### 7-1. 山田建設興業「フェアロード経由」（確定）

車種違いとしては統合せず、山田建設興業のもとに**別現場として仮登録**する。ただし確定データではないため、以下を必須とする。

- 「要確認」フラグを付ける
- 備考に「フェアロード経由・元データ確認必要」と記載する
- 管理画面から後で統合・修正できるようにする
- 元データ（`price_data.json`）は独断で削除・統合しない

### 7-2. 翌日の現場配置の扱い（確定）

推奨案 **(a)引き継ぐ ＋ (c)手動の「本日リセット」ボタン** を採用する。

- リセットボタン押下時は誤操作防止のため確認画面を表示する。確認文：「本日の現場配置をすべて解除し、現場未定に戻します。実行してよろしいですか。」
- リセットは**現場配置のみ**を解除する。社員の所属（`home_department`/`current_department`）・出勤状態・休み状態は一切変更しない。
- 将来「前日の配置を翌日にコピーする」機能を追加できるよう、設計上の余地を残す（フェーズ2Bでは実装しない）。

### 7-3. 現場検索UI（確定）

現場数の増加を前提に検索機能を実装する。

- 検索対象：取引先名／現場名／現場区分／車種／備考
- 画面構成：上部に大きな検索欄／最近使用した現場／よく使用する現場／全現場一覧
- **フェーズ2A**：文字検索と一覧表示のみ実装
- **フェーズ2B**：「最近使用」「よく使用」を当日の現場配置機能とあわせて追加

### 7-4. 部門別／現場別タブ（確定）

出欠ボードに「部門別」「現場別」の2表示を設ける。

- 初期表示は**部門別**（現行運用に近い方）
- 現場別表示で確認できるもの：現場名／取引先名／配置人数／配置されている社員／現場未定の社員／休みの社員
- タブを切り替えても、社員の状態・配置データ自体は変化しない（表示の切り替えのみ）

### 7-5. 要確認データの表示（確定）

- 管理画面上に分かりやすい「要確認」バッジを表示する
- 要確認の理由も確認できるようにする（例：単価欄に日付を含む／電話番号のみ／現場名と発注元の区別が不明／重複または表記ゆれの可能性／車種が不明）
- 要確認データは通常データと分けて一覧表示する
- 管理者が内容を修正した後、「確認済み」に変更できるようにする
- 要確認のままでもデータは削除せず、必ず保持する

### 7-6. 現場区分（確定）

**業務区分（土木／運輸／舗装／その他）と発注区分（公共／民間／不明）の2項目に分離する方針を採用。** 比較は8章参照。

## 8. 現場区分：1項目 vs 2項目分離の比較

現状の6分類（土木／運輸／舗装／民間／公共／その他）は、実質的に「どんな工事か（業務の種類）」と「誰が発注したか（発注元の種類）」という**性質の異なる2つの軸**が1つの項目に混ざっています。

| | 1項目のまま（6分類） | 2項目に分離（業務区分：土木／運輸／舗装／その他　＋　発注区分：公共／民間／不明） |
|---|---|---|
| データ構造 | `Site.category`（1列・6択） | `Site.workCategory`（1列・4択）＋`Site.orderCategory`（1列・3択） |
| 「公共の舗装工事」のような組み合わせ | 表現できない（「舗装」と「公共」が同じ1つの項目の中で排他的な選択肢になってしまうため、どちらか一方しか選べない） | 業務区分＝舗装、発注区分＝公共、と組み合わせて自然に表現できる |
| 将来「公共工事だけ集計したい」等の要件 | 文字列としてしか持っていないため、後から発注区分だけを取り出す処理が必要になり手戻りが大きい | そのまま`orderCategory`で絞り込み・集計ができる |
| 入力の手間 | ボタン1回選択 | ボタン2回選択（業務区分・発注区分をそれぞれ選ぶ） |
| 今の実装コスト | 変わらない（まだ何も実装していない段階） | 列が1つ増えるだけで、実装コストの差はほぼない |

**結論（推奨）**：今はまだ実装前の段階のため、後から分離するより最初から分離した方が明らかに手戻りが少なく、実装コストの差もほとんどありません。**業務区分・発注区分の2項目に分ける設計を推奨します。**
