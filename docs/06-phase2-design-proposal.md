# KoeHaisha フェーズ2 設計提案：現場別管理

`04-phase2-genba-master-idea.md`（アイデアメモ）と`05-price-data-analysis.md`（既存データ分析）を踏まえた設計提案です。**まだ実装していません。内容をご確認いただいた後に着手します。**

---

## 1. フェーズ2の実装範囲（提案）

現場マスター機能を、次の2段階に分けることを提案します。

### 今回のフェーズ2で実装する範囲（提案）

- **取引先・現場・単価のマスタ管理**（登録・編集・一覧・単価の履歴管理）
- **既存の単価表（86社分）のインポート**（`scripts/genba_master_draft.json`を元に、レビューが必要な20件を確認しながら取り込む）

### フェーズ2に含めず、別途切り出すことを提案する範囲

- **配車時に現場を選ぶと単価が自動表示され、ダンプ・運転手を選ぶ一連の配車フロー画面**

理由：この配車フローには「車両マスター」「配車記録（誰がいつどの現場に行ったか）」という、現時点でまだ設計していないデータモデルが必要です。フェーズ1で「土台を作ってから積み増す」という進め方をしてきたのと同様に、まず現場マスター（データの土台）を固めてから、配車フロー（その上に乗る機能）に進む方が手戻りが少ないと考えます。

→ **この範囲分けでよいか、それとも配車フローまで一気に含めるか、後述の「確認が必要な項目」6番でご判断ください。**

## 2. データベース設計（提案）

ご提示いただいた3層構造（取引先・現場・現場ごとの単価）をそのまま採用します。

### Client（取引先・業者マスター）
| カラム | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| name | 文字列 | 会社名（例：㈱イワシタ舗道） |
| isActive | 真偽値 | 取引終了先の非表示用（削除はしない） |

### Site（現場マスター）
| カラム | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| clientId | 参照 | どの取引先の現場か（1取引先に複数現場） |
| name | 文字列 | 現場名（当面は「会社名」または「会社名－車種」等） |
| category | 列挙型 | 現場区分：土木／運輸／舗装／民間／公共／その他 |
| vehicleType | 文字列 | 使用車種（例：10tダンプ、4t車） |
| notes | 文字列 | 備考 |
| isActive | 真偽値 | 使わなくなった現場の非表示用 |

### SitePrice（現場ごとの単価、履歴管理）
| カラム | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| siteId | 参照 | どの現場の単価か |
| dayPrice | 数値(null可) | 昼単価 |
| nightPrice | 数値(null可) | 夜単価 |
| otherPrice | 数値(null可) | その他単価 |
| validFrom | 日付(null可) | 適用開始日 |
| validTo | 日付(null可) | 適用終了日（未設定＝現在も有効） |
| notes | 文字列 | 備考 |

単価を`Site`に直接持たせず`SitePrice`を分けたのは、分析結果にあった「4/2から単価改定」のような**単価改定の履歴を残せるようにするため**です。「現在の単価」は`validTo`が空欄の行を参照します。

### 「4t車」等の車種違いの扱い（提案）

分析の結果、86社中17行が「同じ会社の車種違い料金」でした。これを**同じ取引先の下に、車種ごとに別の`Site`レコードとして登録する**ことを提案します（例：`㈱俵口建設`という取引先の下に「俵口建設－標準」「俵口建設－4t車」という2つの現場）。ユーザー案の`Site.vehicleType`にそのまま収まるため、追加のテーブルは不要です。

## 3. 画面構成（提案）

フェーズ1の社員管理画面（`/admin`）と同じ考え方（大きめのボタン、タップ中心、シンプルな一覧＋フォーム）を踏襲します。

- `/admin/clients` … 取引先一覧・追加・編集
- `/admin/sites` … 現場一覧（取引先ごとにグループ表示）・追加・編集

- インポート結果の確認は専用画面を作らず、`docs/05-price-data-analysis.md`の「要確認20件」を見ながら、上記の管理画面上で1件ずつ内容を直接確認・修正する運用を提案（フェーズ1の方針＝画面を増やしすぎない、を踏襲）

## 4. 単価表データの整形・インポート方法（提案）

1. `scripts/genba_master_draft.json`（今回作成済み・86行の分析結果）を元データとする
2. 開発者が1回限りのインポートスクリプト（`prisma/seed.ts`と同様の考え方）を作成し、開発環境のデータベースに投入する
3. 「要確認」20件・「単価データなし」4件は、金額が抽出できたものはそのまま登録し、注記（日付・国交省・Lゲート等）は`SitePrice.notes`にそのまま残す（自動で「適用開始日」と決めつけない）
4. 金額を含まない2件（電話メモのみ）は単価を空欄のまま登録する
5. インポート後、管理画面で一覧を見ながら内容を確認・修正する

**画面からのアップロード機能（CSV取り込み等）は今回は作らず、開発者による1回限りのスクリプト投入を提案します。** 今後、単価表の更新が頻繁に発生するようであれば、フェーズ2以降で改めて検討します。
