# KoeHaisha フェーズ1 設計提案

`01-photo-analysis-report.md` の分析結果とご回答（赤札＝休み状態、1段目＝土木部門、状態セットは共通、会社・車両割当はフェーズ2以降、休みは専用エリアに自動集約）を踏まえた設計案です。実装前の最終確認用です。

---

## 1. 全体構成

フェーズ1は「出欠札のデジタル化」のみが対象。配車・車両・請求などは対象外ですが、後続フェーズで同じ土台に積み増せるよう、以下の構成にします。

```
[縦型タッチパネル(ブラウザ全画面表示)]
        │  HTTP
        ▼
[KoeHasha Webアプリ (Next.js)]
   ├─ 画面(UI)：出欠札ボード
   └─ API：状態取得・状態更新
        │
        ▼
[DB (SQLite 1ファイル)]
   └─ 社員マスタ／状態マスタ／状態変更履歴
```

- タッチパネル1台（または事務所のPC1台）で完結する構成。サーバー管理・ネットワーク設定が不要（社内に詳しいIT担当がいなくても運用できる）。
- 画面とAPIを同じアプリ内に持つことで、常時起動のタッチパネル1台で完結。
- 将来、複数拠点・複数端末から同時に見る必要が出た場合は、DBをPostgreSQL等に差し替えるだけで拡張可能な作りにしておきます（今は実装しません）。

## 2. DB設計

紙の運用に忠実に、「社員」「状態」「状態を変えた記録」の3つだけに絞ります。会社名・車両番号はフェーズ2以降で追加します。

### employees（社員）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列(UUID) | 主キー |
| name | 文字列 | 氏名（例：土屋博正） |
| department | 'DOBOKU' \| 'UNYU' | 土木／運輸の部門区分 |
| display_order | 整数 | ボード上の並び順（写真の左上→右下の順を再現） |
| current_status_id | 状態への参照 | 現在の状態 |
| is_active | 真偽値 | 退職者等を非表示にするためのフラグ（削除はしない） |
| updated_at | 日時 | 最終更新日時 |

### statuses（状態マスタ）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列 | 主キー（例：`shukkin`） |
| label | 文字列 | 画面表示名（例：出勤） |
| color | 文字列(HEXコード) | 札の色 |
| sort_order | 整数 | 選択ポップアップでの表示順 |

初期データ（案／ご確認ください）：

| label | 色のイメージ | 備考 |
|---|---|---|
| 出勤 | 白 | 通常勤務中（紙の白札に相当） |
| 現場 | 青 | 現場に出ている |
| 休み | 赤 | 本日休み（紙の赤札に相当、最下段に自動集約） |

※「空車」「整備」は車両側の状態のため、会社・車両を扱わないフェーズ1では一旦保留とし、フェーズ2（配車・車両管理）で車両側の状態として設計します。土木・運輸で共通の状態セットとして上記3つを基本案としますが、過不足あればこの場で調整します。

### status_history（状態変更履歴）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列(UUID) | 主キー |
| employee_id | 参照 | 誰の変更か |
| from_status_id | 参照(null可) | 変更前 |
| to_status_id | 参照 | 変更後 |
| changed_at | 日時 | 変更日時 |

紙にはなかった記録ですが、「いつ誰が休みにしたか後から追える」という将来の安心材料として、表示はせず裏側で自動記録だけしておきます（フェーズ1画面には出しません）。

## 3. 画面設計（縦型タッチパネル・1画面のみ）

紙のボードと同じ「一覧して、色で分かる」構成をそのまま再現します。

```
┌─────────────────────────────┐
│  KoeHaisha        2026/07/27 │  ← ヘッダー：日付のみ、シンプルに
├─────────────────────────────┤
│ 土木                          │
│ [村田] [垣﨑] [川脇] [桒野]     │  ← 大きな名札ボタン、現在の色で表示
│ [黒瀬] [小野] [渡邊]           │
├─────────────────────────────┤
│ 運輸                          │
│ [土屋] [長野] [安達] [池田]     │
│ [冨永] [木本] [栢原] [三浦] ... │  ← 写真の並び順をdisplay_orderで再現
├─────────────────────────────┤
│ 休み・待機                     │
│ [○○] [○○]                    │  ← 「休み」にした人が自動でここに集まる
└─────────────────────────────┘
```

- 名札をタップ → 大きな状態選択ボタン（出勤／現場／休み）がポップアップ表示 → タップで即確定。ドラッグ操作は一切なし。
- 「休み」を選ぶと、その名札は自動的に最下段の「休み・待機」エリアへ移動（紙で最下段に札を移していた運用をそのまま再現）。
- 「休み・待機」エリアの名札をタップすれば同じポップアップから「出勤」等に戻せる（元の部門・順番の位置に自動で戻る）。
- 保存ボタンは無し。タップした瞬間に確定・自動保存。
- 文字サイズ・ボタンサイズは離れた場所からでも読める大きさにする（実装時に実機で確認）。

## 4. 操作フロー

1. タッチパネルは常時この画面を表示（起動・ログイン操作は不要）。
2. 状態を変えたい人の名札をタップする。
3. 出てきた選択肢（出勤／現場／休み）から今の状態をタップする。
4. その場で色が変わり（休みなら最下段へ移動し）、操作完了。
5. 他の人も同じ画面を見れば、最新の状況がそのまま分かる。

## 5. フォルダ構成

既存の `scripts/` `output/`（Excel版・別件）はそのまま残し、新しいWebアプリは独立したフォルダに作ります。

```

│   ├── 01-photo-analysis-report.md
│   └── 02-phase1-design.md
├── scripts/            ← 既存（触りません）
├── output/             ← 既存（触りません）
└── webapp/             ← KoeHaisha フェーズ1本体（新規）
    ├── prisma/
    │   ├── schema.prisma
    │   └── seed.ts       # 写真から読み取った氏名・部門の初期データ
    ├── src/
    │   ├── app/
    │   │   ├── page.tsx              # 出欠札ボード画面
    │   │   └── api/
    │   │       └── employees/
    │   │           ├── route.ts          # 一覧取得
    │   │           └── [id]/status/route.ts  # 状態更新
    │   ├── components/
    │   │   ├── DepartmentSection.tsx
```

## 6. 使用技術

| 用途 | 技術 | 理由 |
|---|---|---|
| 画面・API | Next.js（React + TypeScript） | 画面とAPIを1つのアプリで完結でき、将来フェーズ（配車・請求書など）の画面追加もしやすい |
| デザイン | Tailwind CSS | 大きなボタン・色分けを一貫して素早く実装できる |
| データベース | SQLite（Prisma経由） | サーバー管理が不要、タッチパネルと同じ1台で完結。将来複数拠点対応が必要になればPostgreSQLへ切替可能（今は変更しません） |
| 画面表示 | ブラウザのキオスク（全画面）モード | 既存のタッチパネル端末にそのまま表示できる |
