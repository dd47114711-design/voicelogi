# KoeHaisha フェーズ1 設計提案（改訂版・確認中）

`01-photo-analysis-report.md` の分析結果とご回答を踏まえた設計案です。本ドキュメントは実装確定前のレビュー用で、**まだフェーズ1完成扱いにはしていません**。2箇所だけ判断待ちの項目があり（後述）、それ以外はご指摘を反映済みです。

**フェーズ1は札のデジタル化だけを実装します。ただし、将来の配車システムへ拡張することを前提とし、人の状態は「出勤・現場・空車・休み・その他」の5種類を基本とします。**（「整備」は本来は車両側の概念のため、人の状態からは外し、フェーズ2の車両管理側で実装する方針に修正。詳細は2章参照）会社・車両・配車との連携はフェーズ2以降とします。

## 1. 全体構成

フェーズ1は「出欠札のデジタル化」のみが対象。配車・車両・請求などは対象外ですが、後続フェーズで同じ土台に積み増せるよう、以下の構成にします。

```
[32インチタッチディスプレイ(KTC MEGAPAD等、標準ブラウザで表示)]
        │  HTTP
        ▼
[KoeHasha Webアプリ (Next.js)]
   ├─ 画面(UI)：出欠札ボード
   └─ API：状態取得・状態更新
        │
        ▼
[DB (SQLite 1ファイル)]
   └─ 社員マスタ／状態マスタ／状態変更履歴
```

- タッチパネル1台（または事務所のPC1台）で完結する構成。サーバー管理・ネットワーク設定が不要（社内に詳しいIT担当がいなくても運用できる）。
- 画面とAPIを同じアプリ内に持つことで、常時起動のタッチパネル1台で完結。
- 将来、複数拠点・複数端末から同時に見る必要が出た場合は、DBをPostgreSQL等に差し替えるだけで拡張可能な作りにしておきます（今は実装しません）。

### 端末についての方針（確定）

- 主に**32インチのタッチディスプレイ（KTC MEGAPAD等、Android搭載）**に常設して使うことを想定するが、**専用アプリ（ネイティブアプリ）は作らない**。標準的なWebブラウザ（Chrome等）で動くWebアプリケーションとして開発する。
- これにより、将来Windows PCや他のタッチディスプレイ・タブレットなど別端末に変えても、同じシステムをブラウザで開くだけでそのまま使える（特定機種に依存しない）。
- 操作はマウス・キーボードを使わず、**指だけで全操作が完結**することを必須とする（ドラッグ操作なし、タップのみ）。社員管理画面での文字入力もタブレットのソフトウェアキーボードで完結する。
- レイアウト・文字サイズ・ボタンサイズは32インチのタッチディスプレイで離れた場所からでも見やすい大きさを基準にする。

### 将来拡張の大方針（フェーズ1では実装しない）

配車・車両管理・音声入力・運行日報・請求書・売上管理へ将来拡張できるよう、フェーズ1の設計・データの持ち方はそれを見据えた形にしておく（実装はしない）。具体的な配慮は2章「将来の拡張を見据えたレイアウト方針」および3章の社員テーブル設計（`home_department`/`current_department`の分離等）を参照。

## 2. DB設計

紙の運用に忠実に、「社員」「状態」「状態を変えた記録」の3つだけに絞ります。会社名・車両番号はフェーズ2以降で追加します。

### employees（社員）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列(UUID) | 主キー |
| name | 文字列 | 氏名（例：土屋博正） |
| home_department | 'DOBOKU' \| 'UNYU' | **本来の所属**部門（人事上の所属、基本的に変わらない） |
| current_department | 'DOBOKU' \| 'UNYU' | **当日ボードに表示する**部門。通常は`home_department`と同じ値 |
| display_order | 整数 | ボード上の並び順（写真の左上→右下の順を再現） |
| current_status_id | 状態への参照 | 現在の状態 |
| is_active | 真偽値 | 退職者等を非表示にするためのフラグ（削除はしない） |
| updated_at | 日時 | 最終更新日時 |

**「本来の所属」と「当日の配置」を分ける理由**：運輸所属の人が応援で土木の仕事をする（逆も同様）ケースに将来対応するため、所属を2つに分けておきます。フェーズ1では`current_department`は基本的に`home_department`と同じ値で、社員管理画面で編集したときだけ変わります。

**確定**：フェーズ1ではデータの器（2つのカラム）だけ用意します。「今日は運輸で応援」のような日々の部門切り替え操作はボード画面には作らず、`current_department`を変える手段は社員管理画面での編集のみとします。

### statuses（状態マスタ）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列 | 主キー（例：`shukkin`） |
| label | 文字列 | 画面表示名（例：出勤） |
| color | 文字列(HEXコード) | 札の色 |
| sort_order | 整数 | 選択ポップアップでの表示順 |

初期データ（人の状態・基本5種類）：

| label | 色のイメージ | アイコン | 備考 |
|---|---|---|---|
| 出勤 | 白 | ⚪ | 会社にいる（紙の白札に相当） |
| 現場 | 青 | 🔵 | 現場に出ている |
| 空車 | 緑 | 🟢 | 対応可能・配車待ち。フェーズ2の「空車だけ表示」機能の土台になる |
| 休み | 赤 | 🔴 | 本日休み（紙の赤札に相当、最下段の「休み」エリアに自動集約） |
| その他 | グレー | ⚫ | 上記に当てはまらない状態を一時的に表せる逃げ道 |

**「整備」について**：車検・車両整備は本来「車両」の状態であり、人の状態ではありません。フェーズ2で車両マスタを作る際に、車両側の状態（空車／稼働中／整備中 等）として実装します。フェーズ1の人の状態一覧からは外します。

**確定**：人の状態は上記5種類のみとします。「運転手本人が整備作業中」を示す別状態は追加しません。

色だけに頼ると見間違いの原因になるため、色分けに加えて**アイコン＋文字**でも状態が分かるようにします（`statuses`テーブルに`icon`列を追加）。

土木・運輸で共通の状態セットとして、この状態を最初から実装します。会社名・車両番号との連携（フェーズ2の配車機能）は今回実装しませんが、状態の種類自体は将来の配車ロジック（空車のみ表示・現場終了で空車に戻す等）にそのまま使えるよう設計します。

### status_history（状態変更履歴）
| カラム | 型 | 内容 |
|---|---|---|
| id | 文字列(UUID) | 主キー |
| employee_id | 参照 | **誰の**状態が変わったか |
| from_status_id | 参照(null可) | 変更前の状態 |
| to_status_id | 参照 | 変更後の状態 |
| changed_at | 日時 | **いつ**変更されたか |

記録できるのは「いつ・誰の状態が・何から何に変わったか」までです。**フェーズ1では操作した人（誰がタップしたか）を記録する仕組み（ログイン等）がないため、操作者は記録しません。** 将来ログイン機能を追加する際に、操作者を記録する列を追加できる形にしておきます。紙にはなかった記録ですが、後から状態の変化を追える将来の安心材料として、表示はせず裏側で自動記録だけしておきます（フェーズ1画面には出しません）。

## 3. 画面設計（縦型タッチパネル・1画面のみ）

紙のボードと同じ「一覧して、色で分かる」構成をそのまま再現します。

```
┌─────────────────────────────┐
│  KoeHaisha        2026/07/27 │  ← ヘッダー：日付のみ、シンプルに
├─────────────────────────────┤
│ 土木                          │
│ [村田] [垣﨑] [川脇] [桒野]     │  ← 大きな名札ボタン、現在の色で表示
│ [黒瀬] [小野] [渡邊]           │
├─────────────────────────────┤
│ 運輸                          │
│ [土屋] [長野] [安達] [池田]     │
│ [冨永] [木本] [栢原] [三浦] ... │  ← 写真の並び順をdisplay_orderで再現
├─────────────────────────────┤
│ 休み                          │
│ [○○] [○○]                    │  ← 「休み」にした人だけがここに集まる
└─────────────────────────────┘
```

- 名札をタップ → 大きな状態選択ボタン（出勤／現場／空車／休み／その他、それぞれ色＋アイコン＋文字で表示）がポップアップ表示 → タップで即確定。ドラッグ操作は一切なし。
- 「休み」を選ぶと、その名札は自動的に最下段の「休み」エリアへ移動（紙で最下段に札を移していた運用をそのまま再現）。「空車」は待機中であって休みではないため、このエリアには入れず元の部門内に残します（休みの人と空車・待機中の人を混在させない）。
- 「休み」エリアの名札をタップすれば同じポップアップから「出勤」等に戻せる（元の部門・順番の位置に自動で戻る）。
- 保存ボタンは無し。タップした瞬間に確定・自動保存。
- **誤操作防止**：状態を変更した直後、画面下に数秒間「元に戻す」が出るようにし、押し間違えた場合はその場で取り消せるようにします（時間が経過したら消え、以後は改めて名札をタップして変更）。
- 色だけに頼らない：状態は色に加えてアイコン（⚪🔵🟢🔴⚫）と文字ラベルの3重で表現し、見間違いを減らす。
- 土木／運輸のセクションは、状態色と混同しないよう部門ごとに枠線・背景色を分け、境目をはっきりさせる（状態の色分けとは別の中立的な色を使う）。
- 指の太い現場作業員でも押しやすいよう、名札・選択ボタンとも大きめのタップ領域を確保する（前回よりさらに一回り拡大）。

### 将来の拡張を見据えたレイアウト方針（フェーズ1では未実装）

フェーズ2以降、名札に会社名・車両番号・配車情報を追加する予定があるため、フェーズ1の時点で次を満たすレイアウトにしておきます。

- 名札カード（`NameTag`）は氏名・状態だけでなく、後から会社名・車両番号などの補足行を追加してもレイアウトが崩れない大きさ・余白にする。
- カードや状態選択ポップアップは、表示項目が増えることを前提にした縦方向に伸ばせる構造にする（横幅を固定に頼りすぎない）。
- 今回はDBに会社名・車両番号のカラムは追加しない（フェーズ2で設計）。UI側の「入れ物」だけ将来を見越した形にしておく、という位置づけ。

### 社員管理画面（フェーズ1の範囲に追加）

出欠札ボードとは別に、社員の追加・編集・削除・並び替えを行う簡易な管理画面（`/admin`）を用意します。

- 一覧：部門ごとに社員を表示。氏名・本来の所属を確認できる。
- 追加：氏名・本来の所属を入力してタップで追加（画面末尾に追加される）。
- 編集：氏名・本来の所属を修正。
- 削除：退職者等を非表示にする（`is_active`を`false`にするだけで、履歴は残す。完全削除はしない）。
- 並び替え：一覧の行にある「↑」「↓」ボタンをタップして、同じ部門内での表示順を1つずつ入れ替える（ドラッグ操作は使わない）。
- 出欠札ボード（メイン画面）側には目立たない形でリンクを置くのみとし、誤って一般利用者がタップしないよう配置に配慮します。

## 4. 操作フロー

1. タッチパネルは常時この画面を表示（起動・ログイン操作は不要）。
2. 状態を変えたい人の名札をタップする。
3. 出てきた選択肢（出勤／現場／空車／休み／その他）から今の状態をタップする。
4. その場で色が変わり（休みなら最下段の「休み」エリアへ移動し）、操作完了。
5. 数秒間「元に戻す」が表示され、押し間違えた場合はタップして取り消せる。
6. 他の人も同じ画面を見れば、最新の状況がそのまま分かる。

## 6. 使用技術

| 用途 | 技術 | 理由 |
|---|---|---|
| 画面・API | Next.js（React + TypeScript） | 画面とAPIを1つのアプリで完結でき、将来フェーズ（配車・請求書など）の画面追加もしやすい |
| デザイン | Tailwind CSS | 大きなボタン・色分けを一貫して素早く実装できる |
| データベース | SQLite（Prisma経由） | サーバー管理が不要、タッチパネルと同じ1台で完結。将来複数拠点対応が必要になればPostgreSQLへ切替可能（今は変更しません） |

## 7. フェーズ1完成条件（Definition of Done）

「会社でそのまま毎日使えるレベル」を、次の条件で判定します。

| # | 条件 | 対応方針 |
|---|---|---|
| 1 | 端末起動時にアプリが自動起動する | 端末のOSに応じた自動起動設定（例：Windowsのタスクスケジューラ／Linuxのsystemdサービス）を用意し、`webapp/`に起動スクリプトを同梱する |
| 2 | ブラウザがキオスクモードで自動表示される | Chromiumを`--kiosk http://localhost:3000`のようなオプションで自動起動するショートカット／スクリプトを用意する |
| 3 | 再起動後も状態が保持される | SQLiteはファイルとしてディスクに保存されるため、アプリ・端末を再起動してもデータは消えない（保存先を固定パスにして確認する） |
| 4 | SQLiteデータを自動バックアップできる | 1日1回、SQLiteファイルを日付付きでコピーする簡単なバックアップスクリプトを用意する（世代管理は簡易でよい） |
| 5 | 通信がない環境でも使用できる | アプリ・データベースとも同一端末内で完結しており、外部サービスへの通信は発生しない構成にする（インストール時のみインターネットが必要） |
| 6 | 誤操作防止：状態変更直後に短時間だけ取り消せる | 状態変更後、画面下に数秒間「元に戻す」を表示し、タップで直前の状態に戻せるようにする |

## 判断待ちだった2点の回答（確定）

1. 人の状態は「出勤／現場／空車／休み／その他」の5種類に確定。「整備」は人の状態から外し、フェーズ2の車両管理側で扱う。運転手本人用の別状態は追加しない。
2. `home_department`／`current_department`はフェーズ1では**データの器だけ**用意する。ボード画面上での日々の部門切替操作（UI）はフェーズ1では実装しない。`current_department`を変えたい場合は社員管理画面での編集のみ。

これで設計は確定したため、実装に進みます。
